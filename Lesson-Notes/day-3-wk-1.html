Module: Local & Remote Version Control with Git & GitHub

1. Theory: The Big Picture

As software projects scale, managing code changes becomes exponentially complex. Professional software engineering fundamentally relies on Version Control Systems (VCS). Without a VCS, developers resort to creating endless, confusing file copies (e.g., index_final_v2_USE_THIS_ONE.html). Git is the industry-standard distributed version control system that eliminates this chaos by providing a highly detailed, navigable timeline of your codebase.

Git operates through a strict conceptual model of state management. A file in Git is always in one of three local states before being pushed to a remote server like GitHub:

[Textual Diagram: The Four Environments of Git] 1. Working Directory (Untracked/Modified) │ ├── (git add) ──> ▼ 2. Staging Area (Index - Prepared for Commit) │ ├── (git commit) ──> ▼ 3. Local Repository (.git folder - Permanent Local Snapshot) │ ├── (git push) ──> ▼ 4. Remote Repository (GitHub/GitLab - Cloud Storage for Collaboration)

By coupling local Git repositories with GitHub (a cloud-based hosting service for Git repositories), engineers can collaborate asynchronously, manage feature branches, and integrate their code into automated CI/CD (Continuous Integration/Continuous Deployment) pipelines.

2. Theory: Semantic Web (and Legible Code History)

While Git manages the history of your files, the quality of that history is dictated by how you write your code and your commits. Here, the principles of the Semantic Web heavily influence version control best practices.

When you use generic HTML elements like thousands of nested <div> tags, the git diff (the visual representation of what lines changed) becomes a nightmare for other engineers to review during a Pull Request. If you change one <div> in a sea of identical tags, context is lost. However, if you modify an <article> inside a <section id="enrollment">, the Git diff instantly communicates the structural and semantic impact of your change.

Semantic Commits (Conventional Commits)

Just as we use semantic HTML tags to give meaning to content, industry professionals use Semantic Commit Messages to give meaning to code history. A standard commit format looks like this:

  • feat: Introduces a new feature to the codebase (e.g., feat: add GitHub profile input to registration form).
  • fix: Patches a bug (e.g., fix: correct regex pattern for matriculation number).
  • docs: Changes to documentation (e.g., docs: update README with setup instructions).
  • refactor: Code changes that neither fix a bug nor add a feature, but improve structure.

3. Lab: Environment Setup

To connect our local machine to the cloud, we must configure Git globally and establish an authenticated link to GitHub.

Step-by-Step Configuration

  1. Verify Git Installation: Open your terminal and run git --version.
  2. Global Configuration: If you haven't already, bind your identity to Git. These details are baked into every commit you make. 
    git config --global user.name "Your Name"
git config --global user.email "your.email@university.edu"
  3. GitHub Account: Navigate to github.com and create a free developer account if you do not have one.
  4. Authentication: In modern workflows, VS Code seamlessly handles GitHub authentication. When we execute our first git push, VS Code will prompt you to log into GitHub via your browser, securely generating an OAuth token for future terminal commands.

4. Lab: Guided Coding

We will now initialize our project, commit our work, simulate a collaborative environment by creating a branch, intentionally cause a merge conflict, resolve it, and push everything to GitHub.

Step 1: Local Initialization and First Commit

Navigate to your CV/Form project directory in the terminal:

# Initialize the directory as a Git repository
git init

# Check the status of your files
git status

# Stage all files (the dot '.' means 'everything in this directory')
git add .

# Commit the files to the local repository
git commit -m "feat: initialize project with semantic CV and enrollment form"

Step 2: Linking to GitHub

  1. Go to GitHub.com, log in, and click the New Repository button.
  2. Name it practical-se-it-program. Leave it Public. Do not check "Add a README file" (we want an empty repository to push our existing local code into).
  3. Copy the URL provided by GitHub. Run the following commands in your terminal: 
# Rename the default branch from 'master' to 'main' (industry standard)
git branch -M main

# Link your local repository to the remote GitHub server
git remote add origin https://github.com/YOUR_USERNAME/practical-se-it-program.git

# Push your code to the cloud (-u sets the upstream link for future pushes)
git push -u origin main

Step 3: Branching & Simulating a Merge Conflict

Merge conflicts occur when Git cannot automatically resolve differences between two branches—usually because the exact same line of code was edited differently in both branches. We will force this to happen so you can learn how to fix it. 

# 1. Create and switch to a new development branch
git checkout -b dev-branch

Open index.html. Find your <h1> tag and change it to: <h1>IT Student Enrollment 2026</h1>. Save, stage, and commit: 

git add index.html
git commit -m "refactor: update main heading in dev-branch"

Now, switch back to main. The HTML file will revert to its older state in your editor! 

git checkout main

While on main, change the exact same <h1> tag to something else: <h1>Official University Enrollment</h1>. Save, stage, and commit: 

git add index.html
git commit -m "refactor: update main heading directly in main branch"

Now, attempt to merge dev-branch into main: 

git merge dev-branch

Terminal Output: CONFLICT (content): Merge conflict in index.html. Automatic merge failed; fix conflicts and then commit the result.

Step 4: Resolving the Conflict

Open index.html in VS Code. Git has injected conflict markers into your code. It will look like this: 

            <header>
                <<<<<<< HEAD
                    <h1>Official University Enrollment</h1>
                =======
                    <h1>IT Student Enrollment 2026</h1>
                >>>>>>> dev-branch
                </header>

To resolve this, you act as the human arbitrator. Delete the markers (<<<<<<< HEAD, =======, >>>>>>> dev-branch) and keep the exact code you want. Let's keep the dev-branch version. 

            <header>
                <h1>IT Student Enrollment 2026</h1>
                </header>

Once edited and saved, finalize the merge by staging and committing the resolved file: 

            git add index.html
                git commit -m "Merge branch 'dev-branch' into main: resolve h1 conflict"
                git push origin main
