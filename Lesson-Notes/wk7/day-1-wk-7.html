1. Theory: The Big Picture

Up through Week 6, every operation in our Agile Kanban Task Board has been synchronous. When loadFromStorage() reads from localStorage, or when addTaskToDatabase() pushes a task object onto the tasks array inside dist/assets/js/database/mockDb.js, JavaScript executes each line immediately in strict top-to-bottom order and returns the result on the very next instruction.

Real-world web applications rarely operate on in-memory arrays alone. In production, a Kanban board loads tasks from a remote database over HTTPS, saves new cards to a cloud API, and synchronizes team activity logs across browsers. Network requests, disk reads, and timers do not complete instantaneously—they take anywhere from 20 milliseconds to several seconds. Because JavaScript runs on a single main thread inside the browser, waiting synchronously for a slow network call would freeze the entire user interface: buttons would stop responding, CSS animations would stall, and the browser tab would become completely unresponsive.

2. Theory: Semantic Web & Technical Standards

2.1 The JavaScript Runtime & The Event Loop

The JavaScript engine itself (such as V8 in Chrome and Edge) only manages memory allocation (the Heap) and function execution frames (the Call Stack). Asynchronous capabilities like setTimeout(), fetch(), and DOM events are provided by the host browser environment via Web APIs.

  • Call Stack (LIFO): A Last-In, First-Out stack tracking the currently executing function. When refreshDashboard() calls calculateBoardMetrics(), calculateBoardMetrics is pushed onto the stack, executes, and pops off before renderBoardColumns() is pushed.
  • Callback Queue (Macrotask Queue): Holds callbacks from completed Web APIs such as setTimeout, setInterval, and UI DOM events.
  • Microtask Queue: A high-priority queue reserved for Promise callbacks (.then, .catch, .finally) and code resuming after an await keyword.
  • The Event Loop: A continuous coordination loop with one strict rule: Whenever the Call Stack becomes completely empty, drain every single task in the Microtask Queue first before taking one task from the Callback Queue.

2.2 Promise Lifecycle States

Introduced in ES2015 (ES6), a Promise is a standardized JavaScript object representing the eventual completion or failure of an asynchronous operation. Every Promise exists in one of three mutually exclusive states:

State Meaning Settled? Transition Trigger
pending Initial state; the asynchronous operation is still in progress. No Created via new Promise((resolve, reject) => ...)
fulfilled The operation completed successfully and produced a result value. Yes (Immutable) resolve(value) is called inside the executor.
rejected The operation failed and produced a reason (usually an Error object). Yes (Immutable) reject(error) is called or an exception is thrown.

Once a Promise transitions from pending to either fulfilled or rejected, it is settled and can never change state again.

2.3 Async/Await Syntax & Semantic Accessibility

async and await (ES2017) provide syntactic sugar built directly on top of Promises:

  • Marking a function with async guarantees that it always returns a Promise. Returning a plain value automatically wraps it in a fulfilled Promise; throwing an error returns a rejected Promise.
  • Using await pauses execution only inside that async function until the awaited Promise settles, yielding the main thread back to the Event Loop so the UI remains responsive.
  • Accessibility & Asynchronous Feedback: When an interface performs asynchronous work (such as saving a task or loading the board), screen readers and sighted users cannot see background Promises running. Semantically, buttons should temporarily set disabled = true and aria-busy="true" to prevent duplicate submissions, while status regions with aria-live="polite" announce loading or error states cleanly.

if (taskIndex === -1) {

tasks.splice(taskIndex, 1);
syncToStorage();
return true;

function initializeTaskBoard(tasks, createTask, documentRef = document) {
const board = documentRef.querySelector(".board-columns-container");
const form = documentRef.querySelector("#task-form");
const errorMessage = documentRef.querySelector("#task-form-error");
const saveBtn = documentRef.querySelector("#modal-save");
const modal = documentRef.querySelector("#task-modal");

refreshDashboard(tasks, documentRef);

if (form) {
    form.addEventListener("submit", async (event) => {
        event.preventDefault();
        const formData = new FormData(form);

        if (saveBtn) {
            saveBtn.disabled = true;
            saveBtn.setAttribute("aria-busy", "true");
            saveBtn.textContent = "Saving...";
        }

        try {
            const task = await createTask({
                title: formData.get("title"),
                category: formData.get("category"),
                priority: formData.get("priority"),
                desc: formData.get("description"),
                assignee: formData.get("assignee") || "Unassigned",
                status: "todo",
            });

            if (!task) {
                if (errorMessage) {
                    errorMessage.textContent =
                        "Please enter valid task details.";
                }
                return;
            }

            if (errorMessage) errorMessage.textContent = "";
            form.reset();
            if (modal) modal.style.display = "none";
            const updatedTasks = getTasks();
            refreshDashboard(updatedTasks, documentRef);
        } catch (error) {
            console.error("[Task Form] Async save failed:", error);
            if (errorMessage) {
                errorMessage.textContent =
                    "Unable to save task. Please try again.";
            }
        } finally {
            if (saveBtn) {
                saveBtn.disabled = false;
                saveBtn.removeAttribute("aria-busy");
                saveBtn.textContent = "Save Task";
            }
        }
    });
}

return board;

}

Step 4: Coordinate Async Startup in Entry Point (dist/assets/js/app.js)

Update dist/assets/js/app.js so application startup initializes UI listeners immediately (allowing theme toggle and modal controls to work right away) while asynchronously loading saved tasks from loadTasksAsync(): 

import { getTasks, loadTasksAsync } from "./database/mockDb.js";

import { initializeTaskBoard, initializeUI } from "./dom/script.js";
import { createNewTaskAsync } from "./utils/tasks.js";

async function initApp() {
initializeUI();

try {
    const tasks = await loadTasksAsync();
    initializeTaskBoard(tasks, createNewTaskAsync);
} catch (error) {
    console.error("[App Init] Failed to load tasks asynchronously:", error);
    initializeTaskBoard(getTasks(), createNewTaskAsync);
}

}

document.addEventListener("DOMContentLoaded", initApp);

Expected Result & Debugging Notes

  • Expected Result: On page reload, the board renders after a brief 350ms simulated fetch. Clicking New Task and submitting valid data changes the button text to Saving... while the Promise is pending, then closes the modal and updates the board and metrics once the Promise settles.
  • Debugging Note 1 (Forgetting await): If you write const task = createTask(...) without await, task is a Promise object—which is always truthy in an if (!task) check! Always await Promise-returning functions before inspecting their resolved values.
  • Debugging Note 2 (Uncaught Rejections): Every await call that might reject (such as addTaskAsync or deleteTaskAsync) must sit inside a try / catch block so errors surface cleanly in #task-form-error rather than failing silently as unhandled Promise rejections.

6. Debrief and Homework

Key Takeaways

  1. Non-Blocking Architecture: JavaScript executes on a single Call Stack, delegating asynchronous operations to browser Web APIs and coordinating completion via the Event Loop.
  2. Queue Priority: The Event Loop drains all Microtasks (Promise.then, catch, finally, and post-await continuations) before executing the next Macrotask (setTimeout, DOM events).
  3. Promise States: Every Promise starts as pending and settles permanently into either fulfilled or rejected.
  4. Clean Async Boundaries: Keeping simulated latency and storage Promises inside mockDb.js ensures script.js only awaits domain operations and renders updated state without knowing how persistence is implemented.
